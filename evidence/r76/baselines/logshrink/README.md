## Official pipeline and parameters

`python_compression/run.py` = training (`parser/training.py` → LogReducer sampler + template/head-format
learning), segmentation of the input into **100,000-line chunks** (`blockSize = 100000`, identical to our block
law), per-chunk `logshrink.run()` (THULR parser → sequence sampling → commonality/variability analyzer →
column/elastic encoding → `7z a … -m0=LZMA`). Decoder: `decompression/decompress_run.py` → `restore.py` per chunk.

Parameters = paper Sec. 5.1.4 defaults (θ=4, h=20, M=16) = the only active line of the repo's
`run_shell.sh`: `-E E -C -K lzma -V -S -P -wh 20 -th 4 -NC 16 -mt 0.5` (run.py hard-codes sample_rate 0.1).
(The README demo line uses `-wh 50 -th 10`; we follow the paper/experiment script.)

Header length `-L`: **official** = the per-dataset `header_length` dict shipped in
`exp_shell_scripts/run_logshrink.py` (Android 6, Apache 6, BGL 9, Hadoop 5, HDFS 5, HealthApp 3, HPC 6, Linux 5,
Mac 5, OpenSSH 5, OpenStack 7, Proxifier 4, Spark 4, Thunderbird 9, Windows 4, Zookeeper 6); the adapter asserts
at start-up that its copy equals the shipped file. This is LogShrink's only per-dataset setting (the
LogHub `log_format` strings in `utils/config.py` are used only by the LogZip/LogReducer baseline scripts, not by
LogShrink). **generic** = `-L 5`, run.py's own argparse default.

## Adapter (`adapter/ls_run.py`, `ls_segment.py`, `ls_seg_runner.py`)

Per block, fresh processes, no state across blocks, cwd = `code_r76/python_compression` (as run.py):

1. `./parser/sampler.py <block> <block>.sample 0.001` run through `runpy` after `random.seed(0)`
   (training.py would call it unseeded).
2. `./parser/training.py -I <block> -T <tpl>/ -L <L> -m Sam` (= run.py's call; `-m Sam` only skips the internal
   unseeded sampler call of step 1). Templates are trained **per block** on the block itself.
3. `ls_segment.py`: run.py's segmentation loop verbatim with the repo's `utils.util_code.list_write`
   (ISO-8859-1 text read, `strip()`, UTF-8 write). A 100k-line block gives segment 0 plus the trailing empty
   segment that run.py also creates; empty segments are skipped (run.py would feed an empty file to the parser).
4. `ls_seg_runner.py` per non-empty segment: `logshrink.run(...)` with exactly run.py's arguments,
   `random`/`numpy.random` seeded with 0 (PYTHONHASHSEED=0). LogShrink's packer writes `<k>.7z`.
5. `model.7z` = `7z a model template.col head.format -m0=LZMA` — the only template-directory files
   restore.py reads, packed with LogShrink's own packer command. **Counted.**

Native archive `block_NNNNNN.lsz` = `>BB` (flags, n_segments) + `>I` length per segment + `>I` len(model)
+ segment payloads + model (10 bytes of framing for one segment). flags bit0 = block has no terminal LF.
Everything the decoder needs is inside; nothing else is read at decode time.

Archive-only decode (cwd `decompression/`, as decompress_run.py): split the archive, `7za x model.7z`, then per
segment the official per-file command `python3 ./restore_r76.py -I k.7z -O out -T tpl/ -t tmp/ -K lzma`;
concatenate. Decode alignment (tool level, all datasets identical): (a) `restored.decode("utf-8").encode("latin-1")`
(inverse of run.py's ISO-8859-1-read / UTF-8-write), falling back to the raw restored bytes if either step fails;
(b) drop the one LF restore.py appends when flag bit0 is set.

### Decoder bug fixes (`restore_r76.py` + `decompress_r76.py`, generated by `adapter/make_restore_r76.py`)

Decoder only; the encoder and every archive byte are untouched; each fix is an asserted exact string
replacement of the pristine file (diff is printed by the generator). All information used is inside the archive.

1. `load_log()` returned `[""]` for an empty `load_failed.log`/`match_failed.log`, so restore.py's own
   `assert eids_len == len(LoadFailed)+len(MatchFailed)+len(Heads)` fails on every block with zero load
   failures (the unmodified official decoder crashed on Proxifier this way — `explore/runA`).
2. header column files `head_var_col<i>.*` were ordered with lexicographic `sorted()`; with >=11 columns col10
   is read as column 2.
3. the **encoder** (`preprocess.read_parsing_result`) reads THULR's `Head<K>.head` files in lexicographic order
   (Head0, Head1, Head10, Head2, ...), but `restore_heads` consumes columns in THULR order; the permutation is a
   deterministic function of the column count and is undone after `recover_pat`.
   Without 2-3 every dataset with >=11 THULR header columns decodes with scrambled headers (Zookeeper:
   "2015-07-0- 29:17:41,041 728 -  INFO ..."; residual 261 KB -> 3.3 KB on Zookeeper block 0).
4. `load_tempaltes()` recognised a template-id line with `re.search('\[\d+\]\n')` and `len < 10`, so a short
   template content line (" [1]") crashed `int(line[1:-2])`; now the whole-line rule THULR itself uses
   (`regex_match("\[(\d+)\]")`). Changes behaviour only where the original raised (seen with generic L on
   HealthApp: all 3 blocks failed to decode before the fix).
5. `recover_pat()` (decompress.py; header and variable patterns): the encoder's `split_arr()` does not advance past
   a delimiter found at offset 0, so that character stays at the start of the extracted value and is also counted
   in the delimiter run (length k>=2); the decoder emitted value + whole run ("/10.250.19.102" -> "/10/.250.19.102").
   Only the run's last character was consumed as a separator, so the decoder now emits value + run[k-1].
   Identical to the original for k == 1. Checked on 11 saved blocks of 11 datasets (`adapter/compare_decoders.py`,
   `logs/compare_decoders.log`): never worse; residual HDFS 471->299 KB, HealthApp 112->39 KB, Proxifier
   16.5->11.7 KB, Thunderbird 3.1->2.7 KB, Android 13.3->12.7 KB, others equal.

Fixes were found during the smoke/probe runs and installed before any number was reported; each install
stopped the full run and restarted it with `--resume` (native encodes reused byte-for-byte, every decode and
residual recomputed with the final decoder), so every reported block is decoded by the same final decoder
(`restore_r76.py` sha256 `55d05257...`, `decompress_r76.py` `130c7bd2...`, recorded in `campaign.json`).

### Remaining (algorithmic) losses of LogShrink — NOT fixed

Observed on the smoke data: CR of CRLF lines and leading/trailing whitespace are stripped (run.py segmentation
and restore.py `strip()`); multiple spaces inside the header collapse to the most frequent delimiter (Linux
"Jun  9" → "Jun 9"); integers beyond the 28-bit elastic/zigzag range are truncated (Zookeeper id 188978561024 → 0);
leading zeros of some numeric fields are dropped (Proxifier "00:04" → "0:4"). These are lost at encode time.
Hence **native LogShrink is not byte-exact on most LogHub files** and, per the pre-registered rule, is listed as
"not losslessly verifiable" where its SHA fails.

### Supplementary "LogShrink + residual" (adapter-repaired; NOT pre-registered)

`block_NNNNNN.res` = `lzma.compress(body, preset=6)` (xz -6) of per-line corrections between the aligned
restored block and the original (format in `build_residual`): per differing line, index delta, the ASCII
whitespace that `bytes.strip()` removes from the original (lead/trail), and, if the stripped original still
differs, one (prefix, replaced length, inserted bytes) edit; if the line counts differ, the whole original block
(fallback). Empty file = no correction. Repaired decode = archive-only native decode + patch (reads only the
`.lsz`-decoded bytes and the `.res`), SHA-checked per block and full file. Its bytes = `.lsz` + `.res`. The
residual is computed from the same archive-only decode (the restore path is deterministic).

Outputs per dataset: `archives/block_NNNNNN.{lsz,res}`, `blocks/block_NNNNNN.json` (sizes, SHA, stage times,
THULR stats, mismatch examples), `diagnostics/block_NNNNNN/*.std{out,err}` (clipped), `result.json`
(native / repaired: bytes, full ratio, suffix ratio from block 1, lossless blocks, full-file SHA; timing).
Timing: per-block encode = stages 1–5 wall; decode = archive split + restore + alignment; sums are single-worker
seconds. They include the container's slow process creation (~65 ms per fork+exec, measured), which dominates
LogShrink because its elastic encoder spawns `parser/Elastic` + `rm` shells for every column file.

## Checks done before the full run

* **Official driver vs adapter** (`adapter/equiv_check_runA.py`, `equiv_check_runA.json`): the unmodified
  `run.py` (whole-file driver, unseeded; Proxifier is exactly one block) produced a 94,385 B payload; the adapter
  (seed 0) 93,650 B. Wrapped in the same framing and decoded by the same decoder both give the same mismatch
  classes (21,329/21,329 lines differ, all CRLF lines) and both repair to the exact SHA. The size gap is the
  unseeded training sample (different templates).
* **Determinism** (`adapter/determinism_check.py`): Linux, Zookeeper, Proxifier blocks encoded in two separate
  runs have byte-identical extracted payload and model files; the .7z sizes differ by <= 30 B because LogShrink's
  packer stores file mtimes in the 7z header (not normalised; reported sizes are those of the full run).
* **Unmodified official decoder**: crashes on Proxifier (fix 1); with fixes 1 only, Zookeeper headers are scrambled
  (fixes 2-3).

## Timing and full-run feasibility

Per block (single worker, wall, container with ~65 ms per fork+exec): encode 24-160 s, decode 11-130 s, driven
by the number of column files (each costs an `Elastic` + `rm` shell at encode and decode), not by MB:
Apache 4.7 s/MB, Zookeeper 3.6 s/MB, HealthApp 6.1 s/MB, Linux 16.6 s/MB, Proxifier 34 s/MB (encode).
First-block probe (`probe1/`, 2 concurrent processes; encode+decode s/block): Thunderbird 117, Windows 62,
Spark 120, HDFS 56, BGL 71, Android 312. Estimate for all 3,797 blocks with 3 workers (x1.15 contention measured
on the small datasets): Android 1.3 h-cpu, BGL 1.1, HDFS 2.0, Spark 12.8, Windows 22.7, Thunderbird 79
-> about 120 worker-hours -> **~40 h wall on 3 workers**, feasible; Windows then Thunderbird are last.
