# R76：补充基线与对照实验——预注册设计

写于 2026-09-29 01:30 UTC，在看到任何 R76 结果之前。之后如有改动，只追加"变更记录"，不改下面的原文。（本副本只保留实验设计与变更记录，与实验无关的写作安排从略；时间统一换算为 UTC。）

## 目的

补充实验与对照，回答七个问题：

1. 收益来自哪里（归因）；
2. 实际价值（字节、速度、大文件的正式测速）；
3. 主结果只跑一次时的可变性；
4. 基线是否完整；
5. 进化部分的预注册设计；
6. 解码时执行 Python 的安全边界，以及复现材料；
7. 结果的文字表述。

DeLog、Denum、LogShrink、LogPrism、LogFold 都纳入基线：有源代码的直接复现。

## 不变的规则

- 每块 100,000 行，块间无状态。
- 离线训练，在线冻结。
- 不写数据集专用规则；不按结果调常数。
- 每个结果都必须只看存档独立解码，SHA 通过；失败就是失败，如实报告。
- 主表仍是冻结的 SemZip 主结果（R73 pool）。

## A. 外部基线

- **协议**：与 R68 `codec_baseline.py` 相同。每块一个独立进程，完整计入原生存档字节；只看存档解码，逐块和全文件 SHA；16 个文件。报告完整文件比率和后缀比率（第 1 块起）。
- **可复现的日志压缩器**：固定 commit，每个 100k 块上独立运行官方完整流程（包括它自带的解析和训练）。只加块适配和解码对齐，不改算法。
  - Denum：论文引用的官方仓库；
  - LogReducer：论文引用的官方仓库；
  - LogShrink：论文引用的官方仓库（各自固定的 commit 见轨道 README 和 `external/fetch_baselines.sh`）；
  - 如果某工具没有解码器，或者不能逐字节还原，按"不可无损验证"如实列出，不进入无损比率比较。
- **DeLog-generic**：官方 DeLog 用空的 `regex_map`，即关掉按数据集名选择的手写正则，其余设置与 DeLog 相同。用来组成"手写规则 / 无规则 / 合成程序"三方对照。
- **通用压缩器高压缩档**（各档固定，不按数据集选）：
  - `xz -9e -T1`；
  - `zstd -19 -T1`；
  - `zstd --ultra -22 --long=27 -T1`；
  - 第 0 块训练的 zstd 字典：`zstd --train`，默认字典大小，样本为第 0 块按 1,000 行切片。用它以 `-19` 压缩全部块。字典字节每个文件只计一次（对基线有利，会写明）。
- **LogFold、LogPrism**：2026-09-29 01:10 UTC 复查。LogFold 仓库只有 LICENSE 和 README，LogPrism 仓库为空。只列论文公布的数字，标注"仅文献参考，输入身份未核验"，不进入实测表。

## B. 归因

**B1 归因阶梯**：16 个文件，完整文件和后缀都报告：

1. 空程序：纯残差，SemZip 骨干，每块 368 B 语义元数据。R75 `cfb` 的逐块编码组装成完整存档，只看存档解码，SHA 必须通过。
2. SemZip-1：R71，单次合成 c0，不过门。
3. 门控 c0：R73 `qg1c0`，零新 API。
4. 池化选择：主结果。

同时并列 DeLog-generic 和 DeLog。

**B2 无 LLM 的规则库对照**：手写一个与数据集无关的确定性提议器。

- 程序类型在看任何 R76 结果之前冻结，下面是全部：
  - 常见时间戳格式：
    - syslog `Mon DD HH:MM:SS`；
    - `YYYY-MM-DD HH:MM:SS` 带或不带 `,mmm` / `.mmm`；
    - ISO-8601 `YYYY-MM-DDTHH:MM:SS[.fff]`；
    - `YY/MM/DD HH:MM:SS`；
    - `YYYYMMDD HHMMSS`；
    - `HH:MM:SS[.fff]`；
    - 10 位 Unix epoch 秒；
  - IPv4，以及 IPv4:port；
  - 十六进制数；
  - 带单位的大小（B/KB/MB/GB，含小数）；
  - 百分比；
  - 十进制整数和定点数（记录宽度与前导零）。
- 它对第 0 块的每个采样组输出与 LLM 相同模式的候选程序，然后走同一个门、存储拟合和发布流程，最后全文件编码并只看存档解码。
- 设计程序库时不看任何数据集的 LLM 程序。
- 不是 API 调用，也不计入 API 次数。

**B3 表示对照**：R70 的 matched-span surface/latent 对照，改用池化选择后的程序，扩到 16 个文件。

- 12 个正式计时文件用完整文件。
- HDFS、Spark、Windows、Thunderbird 用 D 节的 20 个等间隔抽样块。如果时间允许再跑完整文件，但以抽样块为预注册结果。

## C. 可变性

- **重复完整流程**：对相对 DeLog 优势只有 2–6% 的 HPC、HDFS、Hadoop、Spark，再跑 2 次完整流程。每次都和主结果完全相同：
  - 5 次新合成：c0 T=0，c1–c4 T=0.7；
  - 门控、池化、存储拟合；
  - 全文件编码，只看存档解码。
- 报告 3 次（含原始）的最小值、中位数、最大值，以及对 DeLog 的胜负。
- 原始主结果不替换。
- **无 API 分析**：用已有的逐候选门控结果，画"从 k 个候选中按第 0 块代价选一个"的 best-of-k 曲线（k=1..5，全部组合）。只做计算。

## D. 成本

- **正式计时**：加入新基线，与 R73 `timing_campaign.py` 同协议——12 个文件，3 次，串行，交替顺序，等机器空闲。
- **4 个大文件**：每个文件取 20 个等间隔块，块号为 round(i·(N−1)/19)，i=0..19。所有方法串行计时 3 次，取中位数。写明这是抽样块，不是全文件。
- 补充按字节加权的吞吐。
- 补一个存储与计算成本模型（只做计算）。

## E. 解码安全边界

- **审计**：`python_exec` 在编码和解码时如何执行（命名空间、内建函数、资源限制）。
- **白名单校验**：实现静态 AST 白名单，在程序加载时强制执行：
  - 禁止 import；
  - 禁止以下划线开头的属性和名字；
  - 禁止 `exec`/`eval`/`compile`/`open`/`__import__`/`globals`/`getattr` 等；
  - 禁止 while 循环以外的无界结构。只做报告，不据此改程序。
- **检查范围**：静态检查全部已发布程序，包括 16 个主程序、R75 进化程序和 SemZip-1 程序。
- **全量验证**：启用校验后，对 16 个文件全量只看存档解码，SHA 必须全部通过。任何程序不通过都如实报告。

## 变更记录

- **2026-09-29 05:30 UTC，基线移植结果（在任何新基线压缩比比较之前记录）。**
  - **Denum**（论文引用的官方仓库，commit a3a69756）不能逐字节还原。
    - 仓库只有 C++ 压缩器，官方解码器是 Python 包。按数据集名选择的正则把整段匹配替换成一个标签，只存所有数字拼起来的整数，组宽、分隔位置和前导零都不存。
    - 16 个数据集都构造了反例：两份不同的块得到逐字节相同的存档内容，所以格式本身有损。官方解码器另有丢 CR、丢前导零等问题。
    - 按预注册规则，Denum 列为"不可无损验证"，不进入无损比较，未启动全量运行。呈现方式另定。
  - **LogReducer**（commit 40005419）和 **LogShrink**（commit 59ce4943）的原版都不是逐字节无损：会丢 CR、去掉首尾空白、合并空格、丢前导零；LogShrink 还会截断超过 32 位的整数。原版只在 Apache、OpenStack 等少数文件上逐字节还原。
  - **偏离预注册（如实记录）**：两个移植实现各加了一个"+R"改编变体。它存下每块自己的原文与工具解码结果之间的逐行补丁，补丁字节全部计入存档；只看存档解码，SHA 通过。这超出了设计 A 节允许的"块适配和解码对齐"。
  - **处理方案**：原版比率只作为"压缩比（未验证无损）"单独标注；"+R"改编变体列为改编方法（与 LogLite-BL* 同样的标注），进入无损比较并写明改编方式。
  - **LogShrink 解码器修复**：LogShrink 的解码器另外修了 5 处官方 bug（列文件顺序、模板行匹配等），编码器和存档字节不变，已写入其 README。它在 HealthApp 上的修复版曾经不能还原，以最终全量结果为准。
  - **时间风险**：LogReducer/LogShrink 在 Windows、Thunderbird 上的全量运行可能在 10-02 前跑不完。若到 2026-10-02 04:00 UTC 仍未完成，这两个文件改用 D 节预注册的 20 个等间隔块，并标注"抽样块"。
- **2026-09-29 21:30 UTC，规则库对照的诊断与事后分析（事后，如实标注）。**
  - 按预注册流程，规则库在 15 个已完成文件里有 10 个比空程序还差。原因有两个：
    - 规则库对每个组都会发出通用整数程序；
    - 质量门只逐个删规则、且只在严格变小时删除，从不和空程序比较。例如 HealthApp 上没有任何库内时间戳格式匹配，只剩 14 个通用整数规则，第 0 块变大 3.4 倍。
  - 预注册结果照原样报告。另加一个事后分析"空程序下限"：只用第 0 块判断，库计划的第 0 块比空程序大就改用空程序。
    - 这条规则不改变 SemZip：主结果计划在 16 个文件的第 0 块上都小于空程序，生成脚本里有断言。
    - 规则库加下限后，10 个文件退回空程序，5 个比空程序好（Apache、Hadoop、Linux、BGL、Windows）。
